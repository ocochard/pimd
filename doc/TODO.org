** TODO Check "Ignoring lo, has invalid address 127.0.0.1 and/or netmask 255.0.0.0"

We should allow routing to loopback, just check MULTICAST flag?

A decision rather than code.  config_vifs_from_kernel() skips anything
without IFF_MULTICAST (src/config.c), and the warning above is no longer
printed for an IFF_LOOPBACK interface (src/config.c, in the
inet_valid_subnet() branch), which is what issue #89 changed.  The
interface is still skipped though: inet_valid_subnet() (src/inet.c) rejects
any class A subnet whose first octet is 127, so lo is only usable as a vif
when it carries a non-127 address, or a /32, which skips the subnet check
entirely.  That covers the case people actually want, an RP or a source
address on loopback, so the open question is whether 127/8 should be
allowed at all, or the entry closed as answered.

** DONE Add aliases for common pimctl commands

- pimctl show
- pimctl show if
- pimctl show routes  --> show pim routes
- pimctl show groups  --> show igmp groups

Including some summary features

- pimctl show if
- pimctl show interfaces

Show summary of 'pim int' and 'igmp int', because users don't care about
the distinction between layer-2 and layer-3.

Done, as rows in cmds[] (src/ipc.c) with a NULL description, which keeps
them out of "help" while both matchers still resolve them: "show if" and
"show interfaces" for "show interface", "show routes" for "show mrt", and
"show groups" for "show igmp groups".  The prefix matcher could not have
covered them, string_match() (src/pimctl.c) compares the shorter of the two
words, so "show if" is tested against "show igmp" as "if" vs "ig" and
against "show interface" as "if" vs "in", and matches neither.

The summary is "show summary", a visible command rather than a second
meaning for "show if": having "show if" and "show interface" print
different tables is the kind of trap the aliases exist to avoid.  It prints
one line per interface with state, address, PIM neighbor count, DR, IGMP
version, querier and group count.  "show igmp groups" and "show igmp
interface" were implemented but commented out of cmds[], and are commands
of their own again.

** Experimental kernel MFC (*,G) related:
   If the (S,G) iif or oifs are different from the (*,G) or (*,*,RP)
   iifs/oifs, the resp. (*,G) or (*,*,RP) will delete and disallow
   creating (*,G) MFC. Only after all MRT (S,G) are deleted, the
   corresponding (*,G) or (*,*,RP) will create (*,G) MFC.

** Experimental kernel MFC (*,G) related:
   Right now when the MFC (*,G) total datarate is above the SPT switch
   threshold, the (*,G) MFC will be deleted, and any further cache miss
   will result in (S,G) MFC (the problem is that we must do (S,G)
   monitoring for eventually high datagate sources). Only after all
   (S,G) MFCs expire, the daemon's MRT will stop creating (S,G) MFCs
   (i.e. the next cache miss will result in (*,G) kernel MFC).
   A better selection should be applied to sort out the higher
   datarate sources, and at the same time to have (*,G)MFC as well.
   For example, create few (S,G), and after that create the (*,G). If some
   of the created (S,G) MFC entries have very low datarate, delete them.
